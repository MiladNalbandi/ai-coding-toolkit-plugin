## 2. Block B1 — the per-AC loop

### 2.1 The problem it fixes

Today SDD writes **every** red test (Step 3), implements **everything** (Step 5), and
reviews **once at the end** (Step 7). A 9-AC feature therefore produces one enormous
diff, one review, and one commit. Review findings arrive after all the code is written,
which is the most expensive moment to change it.

v1.8 makes the acceptance criterion — not the feature — the unit of work.

### 2.2 The loop

```
                    ACs from clarify-loop / spec
                              │
                              ▼
        ┌──────────── for each AC-NNN, in order ────────────┐
        │                                                    │
        │   ┌─ RED ────────────────────────────────────┐     │
        │   │ write the test(s) for AC-NNN only        │     │
        │   │ run → MUST FAIL for the right reason     │     │
        │   │ commit  test(AC-NNN): <ac text>          │     │
        │   └──────────────────┬───────────────────────┘     │
        │                      ▼                             │
        │   ┌─ GREEN ──────────────────────────────────┐     │
        │   │ minimum code to pass — YAGNI             │     │
        │   │ run → this AC green, no other AC broken  │     │
        │   │ commit  feat(AC-NNN): <ac text>          │     │
        │   └──────────────────┬───────────────────────┘     │
        │                      ▼                             │
        │   ┌─ GATE (AskUserQuestion) ─────────────────┐     │
        │   │ 7 options — see 2.4                      │     │
        │   └──────────────────┬───────────────────────┘     │
        │          ┌───────────┼───────────┐                 │
        │          ▼           ▼           ▼                 │
        │      approve     refactor    back to RED           │
        │          │      (3rd commit)      │                │
        │          │           │            └──── retry ─────┤
        └──────────┴───────────┴──────────────── next AC ────┘
                              │
                              ▼
              all ACs green → Step 6 refactor (whole feature)
                            → Step 7 review + smoke → Step 8 ADR
```

### 2.3 Commit convention

| Phase | Message | Contains |
|-------|---------|----------|
| RED | `test(AC-003): reject a post with no title` | test files only |
| GREEN | `feat(AC-003): reject a post with no title` | implementation only |
| REFACTOR (optional) | `refactor(AC-003): extract TitleRule` | no behavior change |
| REVIEW FIX | `fix(AC-003): review — validate before authorize` | one finding per commit |

Every commit body carries a trailer so the chain stays traceable both ways:

```
Spec: docs/specs/007-post-bookmarks.md#AC-003
```

**Commit-style knob** — asked once, in Step 0 (see 5.1), stored as `<commit-style>`:

| Option | Behavior | Use when |
|--------|----------|----------|
| `two` (default) | test commit + feature commit per AC | you want the red→green history |
| `squash` | one `feat(AC-NNN)` commit per AC, test+impl together | CI runs on every commit and must stay green |
| `end` | no commits during the loop; one commit after all ACs | you squash-merge anyway |
| `none` | leave everything in the working tree | you commit by hand |

Red commits are **local only** until that AC's green commit exists — the loop never
pushes a knowingly-failing tree.

### 2.4 The gate — the exact option set

`AskUserQuestion`, single-select, re-asked after every non-terminal choice:

```json
{
  "question": "AC-003 is green (2/9 done). Test: test(AC-003) · Impl: feat(AC-003). What next?",
  "header": "AC-003 gate",
  "multiSelect": false,
  "options": [
    { "label": "✅ Approve — next AC", "description": "AC-003 is done. Move to AC-004." },
    { "label": "👤 Human review — show me the diff", "description": "Print the two commits' diff and wait. You can then approve, request changes, or reject." },
    { "label": "🤖 AI review this AC", "description": "Adversarial review of this AC's diff only. Each finding gets Apply / Defer / Reject, then back to this gate." },
    { "label": "📝 Add my recommendation, then AI review on top", "description": "You type a change; I apply it as fix(AC-003), then run the AI review against the amended diff and bring the findings back here." },
    { "label": "♻️ Refactor now (while green)", "description": "Clean up this AC's code with the suite green, commit refactor(AC-003), re-run tests, return to this gate." },
    { "label": "⏭ Approve all remaining ACs", "description": "Run the rest of the loop without gating. A final review still happens at Step 7." },
    { "label": "❌ Reject — back to RED for this AC", "description": "The test or the implementation is wrong. Reset to the red phase for AC-003 with your notes." }
  ]
}
```

Semantics that must be written into the reference file:

* Every option except **Approve**, **Approve all remaining** and **Reject** returns to
  this same gate — the user can chain *AI review → add recommendation → AI review again →
  refactor → approve*. That chain is the point.
* **Add my recommendation** is a two-hop: apply the user's text as a `fix(AC-NNN)` commit
  **first**, then run the AI reviewer on the amended diff, so the reviewer sees the
  recommendation rather than the pre-recommendation code.
* AI-review findings are scoped to this AC's diff. Findings that belong to a different AC
  are recorded and replayed at that AC's gate, not fixed out of order.
* **Reject** resets to RED. If the *test* was wrong, the red commit is amended; if the
  *implementation* was wrong, the green commit is reverted and re-done. If the *AC itself*
  was wrong, exit to the spec's amendment block — never silently edit a frozen AC.
* The gate prints live progress every time:

```
  AC-001 ✔ test+feat   AC-004 ⬜             AC-007 ⬜
  AC-002 ✔ test+feat   AC-005 ⬜             AC-008 ⬜
  AC-003 ▶ at gate     AC-006 ⬜             AC-009 ⬜
  ────────────────────────────────────────────────────
  2/9 done · 41 tests green · 0 skipped
```

### 2.5 The three variants

`ac-loop.md` defines one loop with three orderings so every workflow can reuse it:

| Variant | Order | Used by |
|---------|-------|---------|
| **TDD** (default) | RED → GREEN → gate | SDD Full, SDD + TDD |
| **Test-after** | GREEN (`feat`) → TEST (`test`, must pass) → gate | coding-workflows W6 |
| **Task-scoped** | unit is a plan task `T-04`, not an AC; same phases and gate | coding-workflows W5 (PBV), W1 parallel mode |

Test-after keeps one extra rule: the test is written **from the AC text**, never by
reading the implementation, and the loop asserts it fails when the implementation is
temporarily broken (mutate-and-check) so a vacuous test is caught.

For **parallel** implementation (SDD 5b-par, PBV parallel mode) the loop batches: agents
implement N independent ACs concurrently, then the gate runs **once per AC in order**
after the merge. Ordering of gates is preserved even though the work was concurrent.

## 3. Block B2 — the ASCII diagram vocabulary

A new `coding-workflows/references/diagrams.md` gives every skill the same drawing
vocabulary, so plans stop being walls of prose and code.

### 3.1 Rules

* **Max 80 columns** for any diagram (72 preferred for side-by-side blocks).
  Anything wider wraps in a terminal, in a PR comment, and in a nested list.
* ASCII/Unicode box characters only — no images, no mermaid (the target surfaces are
  terminals and plain markdown files).
* Change markers are fixed: `+` added · `-` dropped · `~` changed · `←` annotation.
* A diagram is **required**, not optional, wherever section 6 says so. If nothing
  structural changes, write `No structural change` — never leave the section blank.

### 3.2 The six templates

**T1 — Table before/after** — the schema diff, required for every
schema-touching change:

```
BEFORE                          AFTER
┌────────────────────────┐      ┌──────────────────────────────────┐
│ posts                  │      │ posts                            │
├────────────────────────┤      ├──────────────────────────────────┤
│ id         bigint PK   │      │ id            bigint PK          │
│ title      varchar(255)│ ═══> │ title         varchar(255)       │
│ body       text        │      │ body          text               │
│ created_at timestamptz │      │ created_at    timestamptz        │
└────────────────────────┘      │+author_id     bigint NULL        │ ← new
                                │+published_at  timestamptz NULL   │ ← new
                                │~title         varchar(255)→text  │ ← widened
                                │-legacy_slug                      │ ← drop M4
                                └──────────────────────────────────┘
  fks:     + author_id → users.id (NOT VALID, validated in M3)
  indexes: + posts_author_id_idx    (btree, author_id)
           + posts_published_idx    (btree, published_at)
                                    WHERE published_at IS NOT NULL
  rows: ~2.4M · est. lock: none (every step online)
```

**T2 — Relationships:**

```
users ──1──<∞ posts ──1──<∞ comments
  │                            │
  └──────────1──<∞ ────────────┘   (comments.author_id → users.id)
```

**T3 — Migration timeline (expand/contract):**

```
 M1 expand        M2 backfill       M3 enforce        M4 contract
 ──────────       ───────────       ──────────        ───────────
 add col NULL  →  fill in batches → NOT NULL + FK  →  drop old col
 deploy A         job (idempotent)  deploy B          deploy C
 reversible       reversible        reversible        IRREVERSIBLE
 lock: none       lock: none        lock: brief       lock: brief
                                    needs A live      ≥1 release after B
```

**T4 — Request/layer flow:**

```
POST /api/posts
  → route → handler(thin) → validator → policy → use-case ──┐
                                                   │        │
                                       repository ─┘   domain event
                                            │
                                        postgres
```

**T5 — Plan / file map** (for PBV and W1 plans):

```
 T-01 schema      database/migrations/2026_09_03_add_author.php   [new]
 T-02 model       app/Models/Post.php                             [edit]
 T-03 validator   app/Http/Requests/StorePost.php                 [new]
 T-04 use-case    app/Actions/CreatePost.php                      [new]
 T-05 handler     app/Http/Controllers/PostController.php         [edit]
      └─ T-04 blocked by T-02 · T-05 blocked by T-03,T-04
```

**T6 — AC progress board** — the block shown at every gate (see 2.4).

## 4. Block B3 — the `database-migrations` skill (new)

### 4.1 Why a skill and not another reference

`spec-driven-development/references/database.md` is 68 lines of good advice with no
procedure, no gates, and no tool wiring. Schema changes are the one class of change that
is genuinely hard to reverse in production, so it earns its own pipeline with its own
approval gates — the same argument that justifies SDD over "just write the code".

### 4.2 Layout

```
skills/database-migrations/
├── SKILL.md                       # D0–D8 pipeline + gates (≤350 lines)
├── references/
│   ├── change-catalog.md          # per change type: recipe, risk,
│   │                              #   rollback, engine notes
│   ├── expand-contract.md         # multi-deploy playbook, backfill
│   │                              #   batching, dual-write/dual-read
│   ├── stack-tooling.md           # Laravel, Alembic, Django, Rails,
│   │                              #   Prisma, Knex, golang-migrate,
│   │                              #   Diesel, Flyway/Liquibase
│   └── testing-migrations.md      # up/down/up drill, prod-like copy,
│                                  #   lock timeouts, CI gate
└── assets/
    ├── migration-plan-template.md # the artefact D3 writes
    └── schema-diff-template.md    # the T1 before/after skeleton
```

### 4.3 The pipeline

```
D0 detect     engine + version, migration tool, existing schema
              (read the migrations dir; use the mcp-toolkit database
               MCP to introspect and to size the tables — row count
               decides the risk class in D2)
   │
D1 inventory  every table/column/index/constraint touched
              → render T1 before/after + T2 relationships
              → GATE: "is this the schema you meant?"
                      (approve / edit / reject)
   │
D2 classify   ┌ additive     new table, nullable col, index     LOW
              ├ tightening   NOT NULL, unique, FK, check        MED
              ├ data-moving  backfill, split, merge, re-type    HIGH
              └ destructive  drop col/table, rename             HIGH
              risk × row count → required plan shape (D3)
   │
D3 plan       write docs/db/NNN-<change>.md from the template:
              T1 diff · T3 timeline · one migration per deploy step ·
              backfill batch size + idempotency · rollback per step ·
              expected lock per step · data-loss statement
   │
D4 safety     GATE (checklist — every box ticked, or waived with a
              written reason):
              □ every step reversible, or the irreversible one is
                named and explicitly accepted
              □ index built CONCURRENTLY / ONLINE where supported
              □ no NOT NULL + DEFAULT rewrite on a large table
              □ FK added NOT VALID then VALIDATED, or equivalent
              □ backfill batched, resumable, throttled
              □ lock/statement timeout set
              □ backup or PITR window confirmed
              □ dry-run on a prod-like copy planned
   │
D5 generate   one migration file per timeline step, with a real down()
              (a down() that throws is allowed only for the contract
               step, and the plan must say so)
   │
D6 verify     up → down → up on a scratch DB · run the suite ·
              assert the new constraints really reject bad rows ·
              EXPLAIN the queries the new index serves (print the
              before/after plan) · time each step on a copy
   │
D7 ADR        column type, index type, denormalization,
              partitioning, a new engine
   │
D8 handoff    return the AC-linked tests + the diagram to the caller
              (SDD step 2.5 / PBV plan step / standalone)
```

### 4.4 How it is entered

| Caller | Entry |
|--------|-------|
| SDD | new **Step 2.5 — Data design & migration plan**, between Contract and Tests |
| clarify-loop | the data probe (B4) returns `<data-scope> = new table / alter / backfill` |
| PBV (W5) | any plan task whose file is a migration routes through D1–D6 first |
| W6 test-after | same as SDD — the plan is written before implementation either way |
| standalone | "add a column", "create a table", "write a migration", "rename …" |

### 4.5 SKILL.md front-matter (draft)

```yaml
name: database-migrations
description: >
  Plan, review, and safely ship database schema changes — creating tables, adding or
  dropping columns, indexes, constraints, foreign keys, renames, type changes, data
  backfills, and the migrations that carry them. Produces an ASCII before/after schema
  diff, an expand/contract deploy timeline, a per-step rollback, and a safety gate before
  any migration is generated. Use whenever a task touches the database schema or moves
  data between shapes — including when a feature spec implies a new table or column.
  Trigger on "add a column", "create a table", "write a migration", "rename this field",
  "add an index", "backfill", "change this column type", "drop this table".
command: /db
```

## 5. Block B4 — clarify-loop learns about data

### 5.1 New section in the Step 0 picker

Insert as option **2.5** in the sections checklist (between ACs and Definition of Done):

```json
{ "label": "2.5 Data & migration impact",
  "description": "Which tables/columns change, new tables, backfills, and the migration plan. Produces AC-D-* criteria and an ASCII before/after diff. Skip only if the change touches no persisted data." }
```

### 5.2 Auto-trigger probe (mirrors the existing identity probe)

**Trigger words:** `table`, `column`, `field`, `schema`, `migration`, `migrate`,
`database`, `db`, `index`, `model`, `entity`, `persist`, `store`, `save`, `seed`,
`backfill`, `postgres`, `mysql`, `sqlite`, `mongo`, `redis`, `foreign key`, `relation`.

**Question (single-select):**

```
Your task mentions "{{matched word}}". Before I write acceptance criteria I need to
know how the data shape changes — these have very different blast radii:

  A) No schema change — new code over the existing shape.
  B) New table(s) only — additive, nothing existing is touched.        LOW risk
  C) Alter existing table(s) — new/changed/dropped columns, indexes,
     constraints on a table that already holds rows.                   MED–HIGH
  D) Data migration / backfill — the shape may or may not change, but
     existing rows must be rewritten.                                  HIGH
  E) New datastore or engine — a cache, queue, search index, or a
     second database.                                                  ARCHITECTURE

If C or D: roughly how many rows are in the affected table(s), and can the app take a
brief write lock on them?
```

Stored as `<data-scope>` + `<row-scale>`. Effects:

* **A** → nothing further.
* **B/C/D** → run the `database-migrations` skill for the plan, emit `AC-D-001…`
  criteria (constraint rejects bad row, backfill is idempotent, rollback restores the
  previous shape), and attach the T1 diagram to the clarify output.
* **E** → recommend the architecture workflow + an ADR before any code.
* Also asked here, once, and carried forward: **connection & config** — which
  environment/connection the change targets, whether a read replica or pooler is in
  play, and least-privilege of the migration user.

### 5.3 New Task Type 7 in `references/task-types.md`

"Database / schema change" — its own question block (current shape, target shape, row
volume, read/write patterns, retention, uniqueness and referential rules, zero-downtime
requirement, who else reads this table) and an assembled prompt template that hands
straight to `database-migrations`.

## 8. Rollout — five phases

Each phase is independently shippable and has its own exit criteria (the plan eats its
own dog food).

```
P1 foundation ──> P2 database ──> P3 clarify ──┐
      │                                        ├──> P5 parity + release
      └──────────> P4 visual ──────────────────┘
```

**P1 — Foundation (the loop).**
Write `ac-loop.md` + `diagrams.md`; add `<commit-style>` to SDD Step 0; rewrite SDD
Steps 3+5 to call the loop.
*Exit:* running SDD on a 3-AC toy feature produces 6 commits, 3 gates, and a progress
board at each gate.

**P2 — Database.**
New `database-migrations` skill + SDD Step 2.5 + spec-template Data model + shrink
`database.md`.
*Exit:* "add a nullable author_id to posts" produces a T1 diff, a 4-step T3 timeline, a
ticked D4 checklist, migrations with real `down()`, and a passing up/down/up drill.

**P3 — Clarify.**
Section 2.5, the data probe, Task Type 7.
*Exit:* a task containing the word "column" triggers the probe before any AC is written,
and emits at least one `AC-D-*`.

**P4 — Visual.**
Diagram mandates in W1/W3/W5/W6 + review reference.

## 9. Risks and the decisions taken

| Risk | Mitigation |
|------|------------|
| Red commits break CI on push | `<commit-style>` knob (`squash` / `end`); red commits never pushed without their green pair |
| Gate fatigue on a 12-AC feature | "⏭ Approve all remaining" option; gates auto-skip for ACs whose diff is under a threshold when the user picked batch mode |
| `spec-driven-development/SKILL.md` is already 734 lines | The loop lives in `ac-loop.md`; SDD Steps 3+5 shrink to a call-out — net SKILL.md should get **smaller**, not larger |
| Two skills both claiming "database" triggers | SDD keeps the *feature* trigger; the new skill owns the *schema change* trigger; both descriptions name the boundary explicitly |
| ASCII diagrams wrap in narrow terminals | Hard 80-column rule, stated in `diagrams.md` and enforced by review |

| Per-AC review costs more tokens than one big review | Reviews are AC-scoped (small diffs); the final Step 7 review stays but has less to find |
